## 2. 控制通道

电视有两条可用的控制通道，二者最终都落到同一套 Android keyCode，但适用场景不同。

| | ADB（`input keyevent`） | UDP 9900（网络遥控） |
|---|---|---|
| 前提 | 需 `adb connect` 保持连接 | 同一局域网即可，无需 adb |
| 延迟 | 即时 | 热态约 2 s；空闲后首包可能 12–15 s |
| 应答 | 有（可回读 `dumpsys input`） | 无（fire-and-forget） |
| 可靠性 | 高，适合精确控制 | 一般，不适合连发 |
| 扩展能力 | 可执行任意 shell 命令、`am start`、`screencap` | 仅按键动作 |
| 待机时 | 断 WiFi，不可用 | 断 WiFi，不可用 |

**选型原则：默认走 ADB，UDP 只补位。** 凡是 ADB 有可靠 keyCode 的按键一律走 ADB；
只有 `power_off` 和 `switch_*` 这类 ADB 无法实现、而遥控器确实存在的动作才走 UDP 9900。
两类动作共用危险动作策略，且需要在配置中显式放行。

### 2.1 ADB 通道

```bash
adb connect xxx.xxx.xxx.xxx:5555
adb -s xxx.xxx.xxx.xxx:5555 shell "input keyevent 3"        # HOME
adb -s xxx.xxx.xxx.xxx:5555 shell "input keyevent 22 23"    # 右键 + 确定
adb -s xxx.xxx.xxx.xxx:5555 shell "dumpsys window windows | grep mCurrentFocus"  # 查前台
```

- Python 侧使用 **`adbutils`** 管理连接与命令执行。
- 注入事件在 dumpsys 中记为 `deviceId=-1`，真实遥控器为 `deviceId=4`。
- 注意：**未知键名不报错，会静默注入 `KEYCODE_UNKNOWN(0)`**；批量注入前建议先回读抽查。

### 2.2 UDP 通道

```python
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.sendto(b'{"CONTROL_ACTION":"home"}', ("xxx.xxx.xxx.xxx", 9900))
```

- 载荷为 UTF-8 JSON，单字段 `CONTROL_ACTION`，无认证、无应答。
- **不要连续轰炸**：重发的包会逐个执行，导致重复按键。
- 发送后无法确认，只能靠画面或 ADB 回读验证。
- 本项目的 UDP 客户端位于 `device/udp.py`，由 `device/control.py` 按动作名路由；
  仅覆盖 `power_off` 与 12 个 `switch_*` 动作，`factory_*`、`ctv_reset`、`screenshot`
  等仍保持拒绝。

### 2.3 按键映射（摘要）

完整清单见 [遥控器按键清单](遥控器按键清单-乐视X4-50.md) 与 [网络遥控](网络遥控-乐视X4-50.md)。

| 功能 | UDP 动作 | ADB keyCode |
|---|---|---|
| 主页 / 返回 / 菜单 | `home` / `return` / `menu` | 3 / 4 / 82 |
| 方向 | `up` `down` `left` `right` | 19 / 20 / 21 / 22 |
| 确定 | `ok` | 23 |
| 音量 ± / 静音 | `volume_up` / `volume_down` / `mute` | 24 / 25 / 164 |
| 频道 ± | `channel_up` / `channel_down` | 166 / 167 |
| 数字 0–9 | `num_0` … `num_9` | 7 … 16 |

### 2.4 危险动作（默认禁止）

以下动作会改变设备状态，实现中应列入黑名单，除非配置显式放行：

- 关机/睡眠：`power`、`power_off`、`POWER(26)`、`TV_POWER(177)`、`SLEEP(223)`
- 切源/复位：`switch_*`、`SOURCE`、`SWAP`、`VGA`、`HDMI`、`CVBS`、`CTV_RESET`
- 工厂模式：全部 `FACTORY_*`
- 截图键 `SCREENSHOT`（会写文件）

网络遥控词表中的对应条目：

| 动作 | 后果 |
|---|---|
| `power` / `power_off` | **关机** |
| `switch_source` / `switch_tv` / `switch_vga` / `switch_cvbs` / `switch_hdmi_0`–`switch_hdmi_3` / `switch_station` / `switch_network_model` / `switch_bit_stream` / `switch_play_mode` | **切换信号源/模式** |

> ADB 侧只有 `power`（keyCode 26，待机/唤醒切换）可用；`power_off` 与 `switch_*`
> 没有可靠 keyCode，现由 UDP 9900 补位。**实测固件不认 `power_off`，只认
> `power`**，因此守护服务对外仍叫 `power_off`，实际发送的 UDP 载荷是 `power`。
> 控制台的「电源 / 待机」按钮走 ADB，「关机」和 12 个信号源/模式按钮走 UDP。
> 项目自带 `config.json` 已将
> `allow_dangerous_actions` 设为 `true` 以启用这些按钮，不需要时改回 `false`
> 即可禁用（同时会隐藏 UDP 动作）。

### 3.1 板块 1：电视连接、控制、监控

- 连接：`adb connect` + `get-state` 健康检查；后台 5 s 重连线程，命令因断线失败时自动重连并重试一次。
  每次 `connect()` 前先做一次 1 s 的 TCP 5555 探测：端口不可达时不创建 `adb` 子进程，
  因此电视关机期间只会产生一次 SYN，而不是每 5 秒拉起 `adb connect`。
- 假死恢复：`get-state` 与命令都带显式超时（adbutils 自带 600 s 默认超时，不能用于健康检查）。
  命令超时视为 adbd 假死——此时 `get-state` 仍可能返回 `device`——立即 `disconnect()` 并重连重试；
  连续两次超时则上报连接错误，由后台重连线程继续恢复。每次重建连接都会递增连接代次，
  桌面守护据此重启可能已假死的 logcat 管道。
- 传输层：默认 `auto`——优先 adbutils，未安装时自动回退到系统 `adb` 命令行，行为一致。
- 控制：`DeviceController` 按动作名路由——ADB 有 keyCode 的走 `input keyevent`，
  `power_off` / `switch_*` 走 UDP 9900；危险动作默认拒绝；包名/Activity 严格校验后再拼入命令。
  启动时若配置了 `activity` 直接用 `am start -n`；否则依次尝试
  `-a MAIN -c LEANBACK_LAUNCHER / LAUNCHER / HOME` 加 `-p <包名>`，由系统解析
  ——Android 6 没有 `cmd package resolve-activity`，不能依赖该命令；
  原桌面这类应用只声明 `HOME` 类别，因此放在最后兜底。
- 监控：
  - 前台 App：`dumpsys window windows | grep mCurrentFocus`（回退 `mFocusedApp`），单次约 1.3 s，**轮询间隔最低 2 s 并缓存**；
  - 屏幕/电源状态：`dumpsys power` 中的 `mWakefulness` / `mScreenOn` / `Display Power`；
  - 在线状态：TCP 探测 5555 端口 + `get-state`；
  - 离线退避：连续离线超过 `device.offline_after_sec`（默认 60 s）后，采样间隔放慢到
    `device.offline_poll_interval`（默认 30 s）；ADB 重连成功会立即唤醒采样线程，
    开机发现仍保持在重连间隔（默认 5 s）级别。
  - 日志事件化：单次探测失败只写 DEBUG；连续 `device.offline_confirm_polls`
    （默认 3）次失败才记一条"关机/离线"INFO，恢复时记一条"开机/恢复在线"INFO。
- 文件操作：`ADBClient.install_apk()` 调用主机侧 `adb -s <serial> install -r <apk>`，
  `push_file()` 调用 `adb push`；两者使用独立的主机命令锁，不会在安装/传输期间阻塞
  状态轮询。即使设备层使用 adbutils，这两个操作仍要求本机有可用的 `adb` 可执行文件
  （由 `device.adb_path` 指定或位于 `PATH`）。
  `read_text_file()` 用带标记行的 `adb shell` 命令读取设备文本文件，
  能在旧版 adb shell 不回传退出码的 Android 6 上区分「文件不存在」与「空文件」。

### 3.2 板块 2：桌面守护与开机接口

桌面守护采用文档验证过的「**外部监听 + 主动拉起**」方案，**设备侧不做任何持久化修改**：

```
logcat 监听 category.HOME 的 START（约 100 ms）
  └─ 去抖 1.5 s
       └─ adb shell am start -n com.peter.tvhome.letv/com.gathin.tvhome.MainActivity
```

已实现于 `letv_daemon/watchdog/`：

- **主通道**：`adb -s <serial> logcat -T 0 -v brief ActivityManager:I *:S` 流式读取，
  匹配 `START u0 {… android.intent.category.HOME …}`（约 100 ms）；`-T 0` 只跟随新日志，
  避免启动时重放缓冲区里的旧 HOME 事件；日志管道断开后 5 s 重连，
  **ADB 离线期间不创建 logcat 子进程**，等连接恢复后再拉起。
- **去抖**：一次 HOME 固件会连发 3 条 START，`debounce_sec`（默认 1.5 s）内只拉起一次，
  并用 in-flight 标记避免 logcat 与轮询同时下发。
- **拉起**：经 `ADBClient.launch_app()` 执行 `am start -n <target>`，与 Web 控制台共用同一 ADB 锁。
- **兜底轮询**：每 `poll_sec`（默认 5 s）读取 `StateMonitor` 的缓存快照（不再强制采样，
  仅启动早期尚无结果时补采一次），仍是 `stock_package` 就拉起；
  启动时补查一次，`poll_sec=0` 可关闭。状态采集失败（如 ADB 命令超时）会记入守护状态的
  `last_error`，并在 Web 面板展示，便于区分「守护没触发」与「ADB 已假死」。
- **连接恢复**：ADB 连接重建后自动重启 logcat 管道，避免旧管道随 adbd 假死而静默失效。
- **PAUSE**：文件存在即暂停（相对路径以配置文件所在目录为基准）；Web 控制台可启停、暂停、恢复。
- **自身事件过滤**：忽略 `pkg`/`cmp` 指向自建桌面的 HOME 日志，避免自我触发。
- 端到端约 1.7 s，原桌面会闪现一次，这是固件 force-stop 导致的**固有代价**。
- 不要试图修改 `key.sys.prop.launcher`、`pm disable-user` 原桌面或启用无障碍服务，均已实测无效。

开机接口：本项目只定义接口（如 `power.on()` 抛 `NotImplementedError` 或在 Web 中置灰），
由外接硬件（WoL、红外、继电器）实现，避免与电视自身的待机断网行为纠缠。

### 3.3 板块 3：Home Assistant 桥接

本项目在局域网内暴露一个简单的 HTTP API（端口可配置），HA 自定义集成
`ha_custom_components/letv_daemon` 负责把它映射为实体。集成**不直接调用 adb**，
所有设备操作都经过本项目 API，便于统一加锁、限流和危险动作黑名单。

| HA 实体 | 能力 | 依赖动作 |
|---|---|---|
| `media_player`（电视本体） | 音量步进、静音切换、信号源 | `volume_up` / `volume_down` / `mute` / `switch_*` |
| `switch`（电源） | 关机；`on` = 屏幕点亮（开机方向为空操作，留给外接硬件） | `power_off` |
| `button`（关机） | 关机；ADB 断开时仍可用（UDP） | `power_off`（退化为 `power`） |
| `select`（信号源） | TV / HDMI 1–4 / AV / VGA；ADB 断开时仍可用 | `switch_*` |
| `remote` | `send_command` 发送任意动作，`turn_on` / `turn_off` | 同电源 |
| `button`（快捷启动） | 每个 `apps` 项一个按钮，点击打开 App | — |
| `sensor`（当前应用） | 前台 App 名称，属性含包名、Activity、屏幕状态、错误 | — |
| `binary_sensor`（在线） | 守护服务是否仍能连上电视 | — |

实现要点：

- **配置流**：UI 添加集成，填写守护主机、端口、可选令牌与设备名；
  保存时访问 `/api/health` 验证。`web.token` 变化会触发重新认证流程。
  轮询间隔（默认 5 s，范围 3–300 s）位于集成「选项」。
- **轮询与可用性**：`DataUpdateCoordinator` 轮询 `/api/state`；一次失败把实体标记为
  `unavailable`，下一轮自动恢复。守护服务可达但电视离线时，`binary_sensor` 为 `off`，
  依赖 ADB 的实体不可用，避免展示过期状态；关机按钮、信号源下拉框
  以及提供 `power_off` 时的电源开关走 UDP，仍保持可用。
- **应用清单**：`button`（快捷启动）的名称与列表来自守护服务
  `config.json → apps`（经 `/api/apps` 读取），集成侧不硬编码 App 名。
- **超时与重试**：GET 在网络错误/超时后重试一次；POST 动作绝不自动重试，
  防止重复按键或重复切源。健康检查 5 s，状态/动作表 10 s，按键/启动 20 s。
- **动作发现**：启动时读取 `/api/actions`，据此决定媒体实体暴露哪些能力；
  危险动作未在服务端放行时，相关实体动作会返回明确错误。
- **状态回写**：电源切换和启动 App 后强制调用一次 `/api/state?refresh=1`，
  普通按键则等待下一轮常规轮询。
- **重启恢复**：实体使用稳定 unique_id 与设备注册表，HA 重启后配置条目与实体自动恢复。
- 完整实体说明、动作名清单与**冻结的 API 契约**见
  [`ha_custom_components/README.md`](../ha_custom_components/README.md)。

此外，`ha_custom_components/letv_tv` 是独立集成，只生成**一个**
`media_player` 实体并注册为 HomeKit Television（accessory 模式）。它的输入源
完全由 `config.json → inputs` 定义（名称、`app`/`key` 动作、用于状态回读的
`target`），选中 App 即调用 `/api/launch`，选中按键类源即发送对应动作；
前台包名/组件名匹配 target 时反向更新当前源，因此手动操作电视也能保持同步。
音量使用 `GET/POST /api/volume`；HomeKit 绝对音量由集成内的运行时兼容补丁
修正（见该集成 README）。详见
[`ha_custom_components/letv_tv/README.md`](../ha_custom_components/letv_tv/README.md)。

HA 运行在Docker，host 网络。本项目与 HA 分离部署，
二者通过网络通信；集成目录复制到 HA 的 `config/custom_components/` 下，
新增集成后需要重启 HA。安装步骤见根目录 [readme.md](../readme.md) 的部署章节。

## 5. 已知限制与坑

1. **不可 root**：任何需要 su 的方案都不可行；`pm disable-user` 等操作会被 `SecurityException` 拒绝。
2. **待机断网**：电视待机（STR）后断开 Wi-Fi，ADB 与 UDP 全部不可用，需外部手段唤醒。
3. **HOME 键被固件接管**：原桌面必然闪现，无法从设备侧消除。
4. **UDP 延迟不稳定**：空闲后首包可能延迟十几秒，重复发送会重复执行。
5. **ADB 无鉴权风险**：5555 端口对局域网开放，建议仅在可信内网部署，必要时用防火墙限制来源。
6. **资源紧张**：内存常年仅剩约 100 MB，电视端不要部署常驻进程，守护逻辑放在外部主机。
7. **IP 由 DHCP 分配**：地址变化会导致守护失效，务必做静态绑定。
